# 论文写作用：3.4 大规模计算的工程化实现（数据支撑稿）

## 1. 先说结论

这次核对后，可以比较明确地说：

1. `artifacts_full/` 不是一个单一的“未优化版本目录”，而是一个混合归档目录。
2. 它同时保留了至少三类关键证据：
   - 原始稀疏矩阵乘法日志：`artifacts_full/run_最原始没有优化版本.log`
   - 向量剪枝日志：`artifacts_full/run_optimized_1.3_优化向量剪枝版本.log`
   - 倒排索引 / IR 重构日志：`artifacts_full/run_optimized_1.3_倒排索引_不适用maxscore版本.log`
3. 当前最终实验目录 `outputs/experiments/标题_摘要_ExactTime_window_1/` 仍然保留了完整日志，可以支撑“最终工程已经可以稳定跑完”的表述。
4. `outputs/experiments/标题_摘要_window3/stage2/diagnostics/` 仍保留了 `Top-K` 和词项规模诊断数据，适合支撑“为什么选 Top30、为什么年份级剪枝有效”的论证。

但也有一个重要缺口：

- `docs/工程化优化思路.md` 中提到的“`2012×2013` 在剪枝后但尚未 IR 重构时耗时 `257.98s`”这一组中间版本运行日志，目前没有在归档目录中找到可直接复核的原始日志文件。这个数字现在只保存在开发备忘录里，不能再当作“当前归档中可直接复核的实验日志”来写。

因此，论文里最稳妥的写法是：

- “原始未优化版本”与“IR 重构后的版本”可以直接用现存日志支撑。
- “中间的剪枝版矩阵乘法”可以用现存剪枝规模数据支撑其方向正确，但若写具体 `257.98s`，应注明这是开发记录中的中间测试结果，而不是当前归档中可复核日志。

### 2.2 最能说明“原始方案不可行”的一组证据

原始版本日志中，最关键的不是“慢”，而是“慢到后面直接不可运行”：

- 在 `artifacts_full/run_最原始没有优化版本.log` 中：
  - `2008×2012` 的稀疏矩阵乘法耗时 `1490.41s`
  - 接着计算 `2008×2013` 时，Scipy 在构造中间稀疏结果时尝试分配 `73.9 GiB`
  - 程序最终抛出 `numpy._core._exceptions._ArrayMemoryError`

这组证据非常适合支撑论文里的判断：

> 原始瓶颈不只是算得慢，而是按年份块直接做稀疏矩阵乘法时，中间结果矩阵的构造成本会在大年份对上直接触发内存崩溃，因此必须同时做问题规模剪枝和计算范式重构。

### 2.3 向量剪枝带来的规模压缩

`artifacts_full/run_optimized_1.3_优化向量剪枝版本.log` 里，以下三年最适合作为论文中的示例：

| 年份 | 剪枝前非零项 | 剪枝后非零项 | 累计降幅 |
| --- | ---: | ---: | ---: |
| 2012 | 12,972,237 | 5,191,305 | 59.98% |
| 2013 | 19,068,184 | 7,439,829 | 60.98% |
| 2020 | 37,749,777 | 12,776,241 | 66.16% |

如果想把“剪枝不是一步完成，而是分层缩减”写得更细，`2020` 年可以直接拆成下面这张表：

| 2020 年步骤 | 非零项 | 相对上一步降幅 | 相对原始累计降幅 |
| --- | ---: | ---: | ---: |
| 剪枝前 | 37,749,777 | - | - |
| 手工停用词后 | 33,879,911 | 10.25% | 10.25% |
| 年份覆盖率阈值后 | 32,469,719 | 4.16% | 13.99% |
| 年内 Top-DF 剪枝后 | 17,054,121 | 47.48% | 54.82% |
| 文档内 Top30 后 | 12,776,241 | 25.08% | 66.16% |

这张表可以直接支撑一个很强的论点：真正起到决定性作用的，不是单一规则，而是“停用词 + 年份级高频词 + 文档内 Top-K”的组合剪枝。

### 2.4 Top-K 保留率：Top30 为什么合理

`outputs/experiments/标题_摘要_window3/stage2/diagnostics/` 下保留了 `Top-K` 权重诊断表。这里的 `avg_squared_weight_sum` 可以直接理解为：对 L2 归一化后的专利向量，仅保留前 `K` 个词后，平均还能保留多少平方权重。

基于当前归档数据（去除 1985 年那个历史文档数为 0 的特例）：

| K | 平均保留平方权重 | 年份最小值 | 年份最大值 |
| --- | ---: | ---: | ---: |
| 10 | 81.21% | 75.67% | 86.05% |
| 30 | 97.65% | 96.92% | 98.56% |
| 50 | 99.90% | 99.76% | 99.98% |

这组数据足以支撑：

> 仅保留每篇专利权重最高的 30 个词项，平均仍能保留约 97.7% 的向量平方权重，因此 Top30 在信息保留与计算规模之间提供了较优折中。

### 2.5 Top-K 对“潜在匹配规模”的压缩

`df_pair_sum.csv` 与 `topk_df_pair_sum_k10.csv` / `topk_df_pair_sum_k30.csv` 给出的不是实际运行时间，而是一个结构性代理量：

\[
\sum_w df_x(w)\cdot df_y(w)
\]

它可以用来近似衡量两个年份块之间因为共享词项而可能发生的倒排扫描压力。

当前归档数据表明：

- 全样本窗口内，`Top10` 后该代理量平均只剩原来的 `2.81%`
- `Top30` 后平均只剩原来的 `29.62%`

几个典型年份对如下：

| 年份对 | 原始 `sum_df_product` | Top10 / 原始 | Top30 / 原始 |
| --- | ---: | ---: | ---: |
| 2008 × 2012 | 13,691,368,850 | 3.21% | 29.91% |
| 2012 × 2013 | 44,992,410,754 | 3.07% | 29.70% |
| 2020 × 2020 | 280,172,631,455 | 3.41% | 34.23% |

这组数据很适合解释为什么 Top-K 会显著降低后续 IR 扫描成本：它并不只是减少每篇文档的词数，还在系统层面显著压缩了跨年份共享词项引出的候选对规模。

### 2.6 IR 重构后的运行时间

`artifacts_full/run_optimized_1.3_倒排索引_不适用maxscore版本.log` 中，以下三组数据最有代表性：

| 年份对 | 文档数 `(Nx, Ny)` | 平均保留词数 `AvgLen` | 总耗时 |
| --- | --- | ---: | ---: |
| 2008 × 2012 | `(89,415, 198,250)` | 26.82 | 7.06s |
| 2012 × 2013 | `(198,250, 288,513)` | 26.19 | 38.33s |
| 2019 × 2020 | `(482,283, 518,979)` | 24.52 | 125.06s |

此外，同一份日志还保留了两个非常适合放入论文正文的诊断量：

| 年份对 | Touched Avg | PostingOps Total |
| --- | ---: | ---: |
| 2012 × 2013 | 18,498.1 | 4,273,554,176 |
| 2019 × 2020 | 32,698.0 | 18,055,571,456 |

这说明 IR 重构之后，大年份对虽然仍然会触发大量倒排扫描，但这些扫描已经被压缩到“逐文档的一维累加器”上完成，不再需要构造全局二维相似度矩阵。

### 2.7 当前最终 exact-time 版本仍然可在小时级跑完

在最终论文使用的 `outputs/experiments/标题_摘要_ExactTime_window_1/` 目录下，日志显示：

## 3. 源码层面：这些优化现在是怎么落地的

这一节主要对应“论文里怎么把方法讲清楚”。

### 3.1 全局词表先做第一轮规模控制

源码位置：

- `patent_quality/vocab.py`
- 参数定义在 `patent_quality/config.py`

实现方式：

1. 在 `build_vocab()` 中先按文档频次统计全局 DF 和年份 DF。
2. 只保留满足以下条件的词：
   - 全局 DF 不低于 `min_term_count=20`
   - 全局文档覆盖率不高于 `max_doc_freq_ratio=0.5`
3. 这一步发生在最终词表构造阶段，属于最外层的全局压缩。

这一步解释了为什么：

- `artifacts_full` 的老版本词表是 `109,474`
- 当前 `标题_摘要_ExactTime_window_1` 的最终词表只有 `80,477`

两者并不完全可直接横比，因为文本范围和样本口径已经不同，但都说明系统在进入向量阶段前就已经做了全局词表约束。

### 3.2 年份级高频词剪枝和文档级 Top-K 剪枝

源码位置：

- `patent_quality/pruning.py`

默认参数：

- `df_ratio_threshold = 0.20`
- `top_df_percent = 0.002`
- `topk_terms_per_doc = 30`
- `use_vectors_filtered_for_bsfs = True`

实际执行顺序与代码完全一致：

1. `_zero_columns_in_csr()` 先把需要删除的列直接在 CSR 矩阵里置零。
2. 先做手工停用词列删除。
3. 再按年份 DF 覆盖率删除 `df_y / N_y >= 0.20` 的词。
4. 再删除该年份中 DF 最高的前 `0.2%` 词项。
5. 最后调用 `_topk_per_row()`，用 `np.argpartition()` 只保留每行权重最高的 `30` 个词。
6. 剪枝结果写到 `vectors_filtered/year=YYYY.npz`。

论文里可以把它概括成：

> 工程实现上，系统先做年份级列剪枝，再做文档级行内 Top-K 剪枝；前者减少“哪些词需要参与匹配”，后者减少“每篇专利需要携带多少词进入后续匹配”。

### 3.3 倒排索引 + 逐文档累加器

源码位置：

- `patent_quality/postings.py`
- `patent_quality/pair_compute.py`
- `patent_quality/similarity.py`

实现细节：

1. `build_postings_for_year()` 将剪枝后的年矩阵转为 CSC 结构。
2. 然后按词项保存四个数组：
   - `ptr`
   - `docs`
   - `vals`
   - `max`
3. `pair_compute.py` 中的 Numba kernel 不再构造全局 `Nx × Ny` 相似度矩阵。
4. 它对年份 `x` 的每一篇专利逐行处理：
   - 读取该行非零词项
   - 通过 `ptr/docs/vals` 找到年份 `y` 中共享该词的候选文档
   - 在一维 `acc` 数组中累加相似度贡献
   - 用 `mark` 与 `touched` 记录本轮被访问到的候选
   - 一行结束就清空 accumulator
5. 年份对只计算一次，结果保存到 `pair_contrib/x=..._y=....npz`。
6. `similarity.py` 在汇总 BS / FS 时复用同一个 `pair_contrib`，分别读取 `contrib_x` 与 `contrib_y`。

这正是工程上最关键的变化：

- 旧方案：直接做大规模稀疏矩阵乘法，并维护全局二维中间结果
- 新方案：只保留逐文档、一维、可回收的累加器

### 3.4 当前生产配置没有启用 MaxScore

源码位置：

- `patent_quality/config.py`
- `patent_quality/pair_compute.py`

当前默认配置：

- `enable_maxscore = False`

日志中也始终显示：

- `MaxScore=False`

这和 `docs/工程化优化思路.md` 里“尝试过 MaxScore，但没有显著变快，最后没保留”是一致的。论文里完全可以把 MaxScore 写成“探索过但未纳入最终实现”的补充说明，而不是正文主方法。

### 3.5 exact-time 最终版是在上述框架上再加“日期边界裁剪”

源码位置：

- `patent_quality/pair_compute.py`

当前 exact-time 版新增但不改变主框架的内容是：

1. 跨年边界年份对采用 `forward_boundary`
2. 同年贡献采用 `same_year_backward`
3. 核心仍然是：
   - `vectors_filtered`
   - `postings`
   - Numba block kernel
   - `pair_contrib` 只算一次再汇总

也就是说，final exact-time 版不是推翻之前的工程优化，而是在原来的可扩展框架上增加了“合法日期区间”的约束。

## 4. 一段可直接放进论文正文的写法

下面这段可以直接改写进论文正文：

> 中文专利全样本计算的主要工程瓶颈，并不只是文档数量大，而是年份块之间的相似度计算会在稀疏矩阵乘法阶段构造规模极大的中间结果。归档日志显示，在原始实现中，经过全局低频和超高频词过滤后，词表规模仍达到 109,474；当对 2008 年与 2012 年专利块（分别为 89,415 和 198,250 篇专利）直接进行稀疏矩阵乘法时，单次计算耗时 1490.41 秒，而继续计算 2008 年与 2013 年时程序因尝试分配 73.9 GiB 中间数组而崩溃。这说明原始方案在大年份对上已无法稳定运行。为解决这一问题，本文在工程上采用了两层优化。第一层是问题规模剪枝：系统先按年份删除覆盖率超过 20% 的高频词，再删除每年 DF 最高的前 0.2% 词项，最后仅保留每篇专利权重最高的 30 个词。现存诊断结果表明，Top30 方案平均仍可保留 97.65% 的向量平方权重，而 2020 年向量非零项则从 37,749,777 降至 12,776,241，累计压缩 66.16%。第二层是计算范式重构：系统不再构造完整的年份间相似度矩阵，而是基于倒排索引逐文档扫描共享词项，并在一维累加器中完成相似度累加后立即释放中间状态。重构后，2012 年与 2013 年专利块的相似度计算耗时降至 38.33 秒，2019 年与 2020 年这样的大年份对也仅需 125.06 秒；整个 40 年窗口下的 BS/FS 计算可以在约 64.8 分钟内完成。最终 exact-time 版本在保留该框架的基础上进一步加入日期边界裁剪后，stage5 计算仍可在 54.7 分钟内完成，说明该指标体系已经具备在中国专利全样本上稳定计算、重复执行和扩展到不同窗口设定的工程可行性。

## 5. 需要在论文中谨慎表述的地方

### 5.1 `257.98s` 这组中间结果目前无法直接复核

`docs/工程化优化思路.md` 中写到：

- 剪枝后但尚未 IR 重构时，`2012×2013` 需要 `257.98s`

目前仓库里没有找到能直接复核这组耗时的运行日志。建议写法：

- 如果要写这个数字，最好标成“开发过程中的中间测试记录”
- 不要写成“当前归档日志显示”

### 5.2 `artifacts_full/stats/` 与 `stats 最原始计算的版本/` 不是所有文件都完全一致

已核对结果：

- `bsfs_year=2012.csv`：一致
- `bsfs_year=2020.csv`：一致

但：

- `artifacts_full/patent_quality_output.csv`
- `artifacts_full/stats 最原始计算的版本/patent_quality_output.csv`

这两个最终整表文件并不完全相同。

因此，论文里可以谨慎写：

> 已抽查验证，优化前后至少在 2012 年和 2020 年的年份级 BS/FS 输出上一致。

但不建议直接写成“整份最终 CSV 完全一致”。

### 5.3 `run_optimized_1.4_倒排索引_不使用maxscore版本.log` 不适合当作主要耗时证据

这份日志主要是在复用已经存在的 `postings` 与 `pair_contrib`，更像是一次快速汇总与导出，不是从头完整重跑。因此它可以辅助说明“缓存复用有效”，但不应该拿来作为“IR 主计算耗时”的核心证据。
