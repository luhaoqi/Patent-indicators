# 阶段1/阶段2提速改造方案

## 1. 背景与目标

当前流水线中，阶段1负责统计 DF 并生成词表，阶段2负责重新分词并按年份落盘 tokens。两阶段都会对同一批专利全文再次执行分词，因此在全量数据上形成了明显的重复开销。

本方案的目标是：

- 在不改变最终输出结果的前提下，减少阶段1和阶段2的总耗时。
- 保持阶段1产出的 DF、词表与现有实现完全一致。
- 保持阶段2产出的 `tokens/year=YYYY.jsonl` 与现有实现完全一致。
- 保持阶段3到阶段6的最终结果完全一致。
- 保留现有断点续跑与阶段划分的使用方式，降低迁移成本。

## 2. 当前实现的耗时来源

### 2.1 重复分词

当前代码中：

- 阶段1在 `patent_quality/vocab.py` 中对每篇文档分词，用于统计全局 DF、分年 DF、每年文档数，并生成最终词表。
- 阶段2在 `patent_quality/vectorizer.py` 中再次对每篇文档分词，用于把每篇专利的 token 序列按年份写入 `tokens/year=YYYY.jsonl`。

这意味着全量数据被完整分词两遍。

### 2.2 用户词典加载成本

项目使用 `jieba.load_userdict(user_dict/merged_96.txt)`，该词典体积较大。主进程初始化本身就有明显耗时；在多进程场景下，worker 进程还会重复初始化 `jieba`，因此用户词典会放大总耗时。

### 2.3 阶段2停用词重复加载

阶段1的 worker 在初始化时加载停用词并缓存。阶段2当前实现中，停用词加载发生在每个 batch 的 worker 函数内，导致同一批停用词文件被重复读取。

### 2.4 阶段2写盘过碎

阶段2当前实现是逐条专利记录打开文件并追加写入 JSONL，这会导致大量小粒度文件打开/关闭操作，I/O 开销较大。

## 3. 结果一致性的约束

本改造不是“近似一致”，而是要求“结果完全一致”。为此必须保持以下语义不变：

- 分词逻辑不变：继续使用当前的 `tokenize()` 实现。
- 数据筛选逻辑不变：仍然只保留 `发明授权`，仍按 `申请号` 去重，仍沿用相同年份解析规则。
- 文本拼接逻辑不变：仍使用现有 `col_text_parts` 与 `text_sep`。
- DF 定义不变：每篇文档中一个词无论出现多少次，DF 只计 1 次。
- 词表生成规则不变：仍按 `min_term_count`、`max_doc_freq_ratio` 过滤，再按词典序排序。
- 阶段2 token 明细不变：token 顺序、重复词保留方式、额外字段内容保持不变。
- 阶段3向量化逻辑不变：仍从 `tokens/year=YYYY.jsonl` 读取 token 明细，只在 `w in vocab` 时构造 TF-BIDF。

## 4. 改造总体思路

核心思路是把“阶段1统计 DF”和“阶段2落盘 tokens”合并为一次全量扫描、一次分词。

也就是说：

- 每篇专利只分词一次。
- 这次分词的结果同时用于：
  - 阶段1的全局 DF / 分年 DF / 每年文档数统计。
  - 阶段2的逐专利 token 落盘。

后续阶段3、4、5、6继续沿用现有输入与算法，不直接改动。

## 5. 具体改造步骤

### 步骤1：统一数据读取入口

当前 `iter_clean_docs()` 和 `iter_docs_with_title()` 逻辑高度重复，只是返回字段不同。第一步先抽出统一的底层迭代器，负责：

- 枚举输入 CSV 文件。
- 按块读取数据。
- 筛选 `发明授权`。
- 按 `申请号` 去重。
- 解析申请年份。
- 拼接文本字段。
- 提取标题与额外字段。

在此基础上：

- 阶段1/2共享同一套数据清洗逻辑。
- 阶段1只消费 `id/year/text` 所需字段。
- 阶段2或合并后的处理同时消费 `id/year/title/text/extra_cols`。

这样做的收益是先消除重复逻辑，便于后续合并分词，同时降低重构过程中的语义漂移风险。

### 步骤2：合并阶段1与阶段2的分词过程

新增一个统一的批处理 worker，输入为一批文档，输出同时包含两类结果：

- 统计结果
  - `df_global_delta`
  - `df_by_year_delta`
  - `docs_per_year_delta`
- 明细结果
  - `token_rows`

其中：

- `df_global_delta` 表示该 batch 内每个词在多少篇文档中出现。
- `df_by_year_delta` 表示该 batch 内每年每个词在多少篇文档中出现。
- `docs_per_year_delta` 表示该 batch 内每年保留的专利数。
- `token_rows` 表示该 batch 内每篇专利对应的 JSONL 落盘对象。

每篇专利在 worker 内只做一次分词：

- 用 `toks` 直接生成阶段2所需 token 明细。
- 用 `set(toks)` 生成阶段1所需 DF 统计。

这样就去掉了阶段2对全量数据的第二次分词。

### 步骤3：统一 worker 初始化缓存

将阶段1和阶段2共用同一个 worker initializer，初始化以下内容：

- `jieba` 基础词典。
- 用户词典。
- 停用词集合。

原则是每个 worker 只初始化一次，后续 batch 直接复用缓存。

具体要求：

- 不在每个 batch 内重复调用 `load_stopwords()`。
- 非必要情况下，不在主进程额外做一次完整 `jieba` 初始化。

这样可以降低：

- 大词典加载开销。
- 停用词文件重复读取开销。
- batch 间重复初始化的额外成本。

### 步骤4：保留阶段2 token 文件格式与顺序

为了保证阶段3及之后结果完全一致，阶段2的 token 落盘必须保持以下不变：

- 文件命名不变：仍为 `tokens/year=YYYY.jsonl`
- 单行 JSON 结构不变：仍包含 `id`、`title`、`tokens` 以及 `extra_cols`
- token 序列顺序不变
- 同一 token 的重复出现次数不变
- 行顺序不变

行顺序之所以重要，是因为阶段3会按文件中的行顺序生成矩阵行号和索引文件。如果 token 文件顺序变化，后续 `index/year=YYYY.csv` 的行号可能变化，虽然数学结果可能等价，但就不是“完全一致”。

因此合并后仍应维持与现有 `Pool.imap()` 相同的有序 batch 返回方式，不使用 `imap_unordered()`。

### 步骤5：优化 JSONL 写盘方式

在不改变文件内容的前提下，优化写盘粒度：

- 当前实现：每条记录 `open -> write -> close`
- 改造后：每个 batch 内按年份分组，拼成多行字符串后一次 append

约束：

- 文件内容逐行保持与当前实现一致。
- 保持同一批次内部的记录顺序。
- 保持不同批次之间的写入顺序。

这样能显著减少系统调用次数和文件句柄反复打开关闭的成本。

### 步骤6：保留现有阶段划分，对外接口尽量不变

从工程使用角度，建议保留 `pipeline.py` 里的阶段1和阶段2概念，不直接把用户看到的阶段合并掉。

推荐做法：

- 阶段1内部完成：
  - DF 统计
  - vocab 生成
  - token 落盘
- 阶段2改成：
  - 对 token 产物的完整性检查
  - 或仅作为兼容性 checkpoint 标记

这样做的好处是：

- 外部调用方式不需要大改
- checkpoint 结构基本兼容
- 旧日志阅读习惯不需要完全推倒

如果后续确认稳定，也可以在第二阶段再考虑把日志文字重命名得更精确。

### 步骤7：将“等价性测试”作为重构的前置条件

在正式替换旧实现前，先增加一个针对小样本的回归测试，用于比较新旧实现的中间产物和最终结果是否完全一致。

建议比较以下文件：

- `df/global_df.json`
- `df/term_df_year=*.json`
- `vocab/final_vocab.json`
- `tokens/year=*.jsonl`
- `vectors/year=*.npz`
- `index/year=*.csv`
- 最终 `patent_quality_output.csv`

比较原则：

- JSON/CSV/JSONL：做结构或逐行完全一致比较
- NPZ：比较稀疏矩阵的 `shape`、`indptr`、`indices`、`data`

只有在小样本回归完全一致后，才允许切换到全量运行。

## 6. 分阶段实施顺序

推荐按以下顺序实施，避免一次性改动过大：

### 第一阶段：低风险优化

先做不会改变整体结构、但能直接提速的改动：

- 将阶段2停用词加载迁移到 worker initializer
- 将阶段2写盘改为 batch 内按年份缓冲写入
- 评估并减少主进程不必要的 `jieba` 初始化

这一阶段风险低，容易验证，也能先拿到一部分提速收益。

### 第二阶段：合并一次分词

在第一阶段稳定后，进一步实施核心改造：

- 统一数据入口
- 统一 worker 输出结构
- 一次分词同时产出 DF 和 token 明细
- 调整 pipeline，使阶段1内部同时完成原阶段2的 token 产出

这一阶段是主要收益来源，也是重构重点。

### 第三阶段：全量回归验证

在小样本验证通过后，使用一套完整实验目录进行全量回归，比较：

- 阶段1产物
- 阶段2产物
- 阶段3向量
- 最终 CSV

只有当全量结果完全一致时，才将旧实现移除或废弃。

## 7. 风险点与控制措施

### 风险1：token 文件顺序变化

风险：

- 影响阶段3矩阵行顺序
- 影响 `index/year=YYYY.csv`
- 进而导致最终 CSV 行顺序变化

控制措施：

- 保持 `imap` 有序返回
- 严禁使用无序聚合
- 在回归测试中逐行比较 token 文件

### 风险2：DF 统计语义被误改为 TF

风险：

- 如果误用 `toks` 而不是 `set(toks)` 统计 DF，会直接改变词表与后续 IDF

控制措施：

- 在统一 worker 中显式保留 `seen = set(toks)` 逻辑
- 对 `global_df.json` 和 `term_df_year=*.json` 做结构比较

### 风险3：筛选顺序或去重逻辑改变

风险：

- 可能影响保留的样本集合，导致全链路结果变化

控制措施：

- 抽取公共迭代器时只搬运已有逻辑，不改判断顺序
- 对小样本与全量样本都比较 `docs_per_year`

### 风险4：多进程写盘引入并发问题

风险：

- 如果让 worker 直接写文件，可能引发顺序不稳定或文件竞争

控制措施：

- 仍由主进程统一写盘
- worker 只返回结果，不直接落文件

## 8. 预期收益

预期收益主要来自三部分：

- 去掉阶段2对全量数据的第二次分词
- 去掉阶段2每个 batch 的停用词重复加载
- 减少阶段2逐条 JSONL 写盘的碎片 I/O

其中，去掉第二次全量分词是最大的收益来源。对于包含大规模用户词典和数百万文档的场景，这一项通常会带来最明显的总耗时下降。

## 9. 验收标准

改造完成后，验收标准应为：

- 小样本 smoke test 通过
- 新旧实现中间产物完全一致
- 最终 `patent_quality_output.csv` 完全一致
- 阶段1+阶段2总耗时显著下降
- 不破坏现有 checkpoint 和断点续跑体验

## 10. 建议的落地顺序

如果按最稳妥的路径推进，建议顺序如下：

1. 先补回归测试，锁定“完全一致”的判定标准。
2. 先做阶段2的停用词缓存与批量写盘优化。
3. 再合并阶段1和阶段2的一次分词流程。
4. 最后跑小样本回归，再跑全量回归。

这样可以把风险压到最低，同时逐步拿到性能收益。
